# DATA_MODEL
Status: Phase 2.0 canonical definitions (authoritative until superseded by a later versioned contract).

## Core identity model
- **Principal**: authenticated actor identity that can submit intents and read filtered data.
  - Examples: human player, GM operator, DM agent, god agent, NPC agent, system service principal.
  - A principal is not world-state fiction by default.
- **Entity**: any persistent world object represented in state.
  - Examples: PC, NPC, monster, item, location, shop, faction, deity avatar.
  - An entity may be controlled by one principal at a time.

### Principal vs Entity rules
1. Principals are for **authorization + visibility**. Entities are for **simulation state**.
2. A principal may control zero or more entities over time.
3. An entity has at most one active `controller_principal_id` at a time.
4. Control does not imply ownership. Ownership is represented by explicit domain fields (e.g., property ownership tables).
5. DM service actions use a dedicated DM principal and must still write auditable ledger records.

## Campaign hierarchy
- **Campaign**: long-lived container for narrative continuity and persistent state.
- **Session**: bounded runtime slice inside a campaign (play date / run instance).
- **Encounter**: tactical sub-context inside a session, typically for initiative and turn order.

### Hierarchy constraints
1. A session belongs to exactly one campaign.
2. An encounter belongs to exactly one session.
3. Exactly one encounter can be `ACTIVE` per session at a time.
4. Entities are campaign-scoped; participation in encounter is represented by encounter slots.

## Mode state machine
Allowed modes:
- `EXPLORATION`
- `SOCIAL`
- `COMBAT`
- `CUTSCENE`
- `PAUSED`

Transitions (GM-controlled unless emergency system pause):
- EXPLORATION ↔ SOCIAL
- EXPLORATION → COMBAT
- SOCIAL → COMBAT
- COMBAT → EXPLORATION
- any mode ↔ CUTSCENE
- any mode → PAUSED
- PAUSED → prior mode (or GM-selected next mode)

Rules:
1. COMBAT activation is explicit (never inferred automatically).
2. COMBAT loop enforces initiative and turn gating.
3. CUTSCENE disables deterministic combat actions except explicitly allowlisted administrative actions.
4. PAUSED blocks state-mutating intents except GM/system administrative intents.

## Controlled_By handoff semantics
Fields:
- `controlled_by` enum: `HUMAN`, `AI_DM`, `AI_NPC`, `AI_GOD`, `SYSTEM`, `NONE`
- `controller_principal_id` UUID nullable
- `control_version` bigint monotonic

Handoff contract:
1. Handoff is performed through a transactional command (`handoff_control`).
2. Preconditions:
   - requestor has authority over source and destination control policy
   - entity is not locked by an active commit in same encounter tick
3. Effects:
   - increment `control_version`
   - write ledger `CONTROL_HANDOFF` with previous/next controller and authority reason
4. Conflict rule: stale `control_version` handoff requests are rejected.
5. During COMBAT, handoff is deferred until turn boundary unless an override permission is present.

## Canonical terminology (single-definition glossary)
- **Intent**: proposed action from a principal before deterministic validation.
- **Reaction**: bounded response window action linked to a triggering event.
- **Intervention**: privileged contract-bound effect (e.g., blessing/curse) with authority and cost.
- **State Delta**: deterministic world mutation artifact generated by services.
- **Visibility Scope**: resolved read audience encoded into ledger `visible_to`.
