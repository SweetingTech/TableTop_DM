# Repository guidance for coding agents

## Mission

TableTop DM is a local-first tabletop application and deterministic simulation platform. Preserve
the constitutional boundary: models and clients may propose, but typed authorized kernel code is
the only path to canonical mutation.

This file applies to the entire repository. A more specific `AGENTS.md` may add instructions for
a subtree but must not weaken the invariants below.

## Read before changing code

1. Read `README.md` for product behavior.
2. Read `docs/ARCHITECTURE.md` and `docs/SIMULATION_KERNEL.md` for invariants.
3. Read `docs/API_AND_WORKFLOWS.md` for role and API behavior.
4. Read `docs/OPERATIONS.md` before migrations, Compose, security, or storage work.
5. Read `docs/TESTING.md` before choosing verification lanes.
6. Inspect `git status` and preserve unrelated user changes.

## Architectural rules

- Keep account, actor, persona, embodied entity, mind state, and runtime assignment distinct.
- Keep canonical truth, observation, belief, memory, relationship, and narration distinct.
- Route world mutations through a registered typed command.
- Validate world/run/branch lineage before handler execution.
- Require world-scoped capability and entity control; never union authority across worlds.
- Canonical writes require commit authority. Trial branches remain isolated.
- A model returns a typed proposal from an allowlist. It never applies deltas or writes storage.
- Record seeds and persona/policy/prompt/model/runtime versions for reproducible decisions.
- Preserve idempotency: a retry returns the original receipt rather than executing twice.
- Persist projection, command, event, and outbox atomically.
- Derive observations and relationships from visible same-branch source events.
- Never expose `secret_state`, password/session material, private DM notes, or hidden evidence in
  public projections, telemetry, exceptions, or logs.
- Treat synthetic results as hypotheses, not human ground truth.

## Identity and authorization rules

- `ADMIN` is global; `DM` and `PLAYER` are per-world roles.
- UI route hiding is convenience only. Enforce roles server-side.
- Simulation capabilities are not interchangeable with product roles; synchronize them through
  the identity repository's explicit world grants.
- Do not weaken the forced first-login password change.
- Do not remove the final-administrator safeguards.
- Store passwords with the existing `scrypt` helper and sessions as token hashes.
- Browser sessions use HTTP-only cookies. The operator token is automation compatibility, not a
  human login mechanism.
- Local/reference authorization and durable/RLS authorization must have matching outcomes.

## Database and migration rules

- Never edit an applied migration. Add the next numbered file.
- Migration SQL must support a clean install and upgrade from the immediately prior schema.
- The migration owner and runtime role remain separate.
- Protected runtime tables use least privilege and, where actor-scoped, forced RLS.
- Set `app.actor_id` transaction-locally before protected durable access.
- Use composite foreign keys for world/branch/run/entity consistency.
- Evidence and ledger tables are append-only unless consent deletion is an explicit requirement.
- Add integration tests for every new constraint, policy, trigger, grant, rollback, and restart
  path.
- Update the wheel verifier if packaged migration expectations change.

## Frontend rules

- Use the typed client adapters under `frontend/src/features/*/api.ts`.
- Preserve role-aware navigation and server-side authorization parity.
- Accessible labels, keyboard operation, focus behavior, loading/error/empty states, and mobile
  layout are required behavior.
- Do not silently turn authorization or server errors into demo data.
- Demo fixtures are for reference-mode interface inspection and must be visibly labeled.
- Long UUIDs/hashes need wrapping; tables need owned overflow containers, not document overflow.
- Build with `npm --prefix frontend run build`; commit the resulting current `static/v2` bundle
  when frontend source changes.

## Python and contract style

- Target Python 3.11 and keep public data boundaries typed with Pydantic/dataclasses.
- Prefer pure deterministic handlers and explicit immutable return values.
- Inject repositories/providers behind protocols instead of importing infrastructure into domain
  policy.
- Use stable ordering and hashes; never depend on unordered iteration for reproducible output.
- Use timezone-aware UTC timestamps.
- Keep API error codes stable and avoid leaking private diagnostic data.
- Use `rg`/`rg --files` for discovery and `apply_patch` for source edits.

## Verification expectations

Run the narrowest relevant tests while iterating, then the proportional gate before handoff.

Fast repository gate:

```powershell
uv run python scripts/test.py fast
uv run mypy kernel persona cognition population experiments domains identity infra main.py
```

For migration, RLS, durable repository, identity, replay, worker, or restart changes:

```powershell
$env:TTDM_INTEGRATION = '1'
uv run pytest -m integration -v
```

For user-visible or routing changes, run frontend lint/tests/build and the relevant Playwright
journey against a ready stack. For packaging changes, build a clean wheel and run
`scripts/verify_wheel.py` with the wheel path as its positional argument.

Never claim a lane passed unless it ran successfully in the current worktree. Report skipped
lanes and why.

## Generated and local-only paths

Do not commit:

- `.env`, `.local-run/`, `.claude/`, caches, virtual environments, or `*.egg-info`;
- `frontend/node_modules/` or TypeScript build metadata;
- `build/`, test screenshots/traces, `artifacts/`, or burn-bag files;
- passwords, tokens, cookies, private notes, or database dumps.

Do commit current `static/v2/` production assets after a frontend change because the Python image
and wheel serve that bundle.

## Documentation maintenance

Update documentation in the same change when behavior, routes, roles, configuration, stores,
ports, migrations, commands, or test lanes change:

- product/setup: `README.md`;
- architecture/invariants: `docs/ARCHITECTURE.md` and `docs/SIMULATION_KERNEL.md`;
- routes/workflows: `docs/API_AND_WORKFLOWS.md`;
- deployment/security: `docs/OPERATIONS.md` and `docs/NETWORK_AND_DEPLOYMENT.md`;
- gates: `docs/TESTING.md`;
- release summary: `CHANGELOG.md`.

Use relative Markdown links and Mermaid for diagrams that should render on GitHub. Verify local
links before handoff.

## Git and safety

- Preserve unrelated work in a dirty worktree.
- Do not use destructive reset/checkout commands to discard user changes.
- Validate exact paths before recursive deletion or volume reset.
- Do not push, merge, tag, publish, or change remote state unless the user authorizes it.
- Keep commits focused and describe migration/security implications in the message or PR.
